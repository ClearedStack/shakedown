# Shakedown specification

> Automated 5-condition verification worker that tests built static tools for offline execution, strict CSP, zero tracking, worked examples, and public citations before catalog publication.

**Status: built (`v0.1.0-draft`, contract `v1`).** This specification describes Shakedown's static 5-condition verification suite, Muster worker loop, local `/var/spool/cs` staging, and hardened `cs-workers` deployment manifests.

The same text is published at [clearedstack.com/platform/shakedown/](https://clearedstack.com/platform/shakedown/). To change the specification, change it here and say why.

## Overview & Role

Shakedown is the automated quality-assurance worker in the `cs-workers` namespace (`ownerRepo: Shakedown`, version `v0.1.0-draft`). Split out of the original Stage 9 (List) design, its sole responsibility is to run the deterministic **5-condition verification suite** against every static tool bundle built by Keelworks from a Moldloft repository.

Like every worker in the pipeline, Shakedown is a 100% deterministic Go service with zero AI at runtime. A tool cannot enter the `live` catalog unless every check in the suite passes.

Shakedown runs under the Standard Kubernetes priority class so it yields cleanly if High-priority control-plane pods (Logbook, Muster, Conn, Plainforge, Lazarette, Shipkeeper) need memory on a 4 GiB `k3s` node.

## Interfaces & State Transitions

Shakedown never connects directly to Logbook or holds database credentials. It polls Muster over cluster-private HTTP using its Kubernetes ServiceAccount identity (`lease`, `heartbeat`, `complete`, `fail`, `needs_subtool`), always draining `urgent` before `normal` and `normal` before `backfill`.

1. **Input state (`building`):** Picks up items whose static bundle has been generated by Moldloft and compiled without Docker by Keelworks (using rootless BuildKit).
2. **5-condition verification suite (supports both Moldloft `moldloft.json` bundles and standalone `shakedown.json` bundles):**
   - **Offline execution:** Confirms the tool loads once and operates with the network disconnected, inspecting HTML, CSS, JavaScript, JSON, and Markdown (`.md`) files so all lookup tables, rates, assets, and regulatory dates resolve inside the repository (permitting external URLs only on passive links and declared `data/tool.json` citation URLs in `js/data.js`, plus integrity checks on `moldloft.json` SHA-256 digests).
   - **Strict Content Security Policy:** Verifies `connect-src 'self'`, `default-src 'self'`, and `form-action 'none'` so the browser blocks any outbound data transfer or remote asset fetch.
   - **Zero tracking or accounts:** Confirms zero sign-in walls, analytics scripts, cookies, visitor counters, or third-party beacons, and verifies any local browser storage usage is disclosed with a clear-data control.
   - **Worked-example assertions:** Executes hand-calculated worked examples, boundary edge cases, and synthetic test fixtures across all four stack templates (`calculator`, `checklist`, `validator`, `decision-tree`) inside Shakedown's deterministic, memory-capped Go JavaScript interpreter (`internal/js`), including `data/tool.json` <-> `js/data.js` and `tests/worked-examples.json` <-> `tests/worked-examples.js` mirror checks.
   - **Citations, scope limits, and MIT license:** Checks that every calculation, checklist item, validator column/table, or decision-tree branch cites its official source and has worked-example coverage, states scope exclusions and a non-advice or footer notice, and includes an MIT `LICENSE` file.
3. **Output transition:** Stages the signed verification result in `/var/spool/cs` and reports completion to Muster, hand-off ready for Chartroom to transition `building` → `live`. If regulatory ambiguity blocks verification, the item moves to `parked`.

## Sub-Tools & Failure Modes

Shakedown defines **no per-case sub-tools** (`subTools: []`) because the 5-condition verification suite is universal across all stack templates (`calculator`, `checklist`, `validator`, `decision-tree`).

| Error Code | Trigger | Pipeline Behavior |
| --- | --- | --- |
| `E_PARSE` | Missing `LICENSE`, invalid CSP policy, failed worked-example assertion, or malformed bundle | Refuses to guess; logs sanitized failure to Muster and halts item before catalog publication. |
| `E_TIMEOUT` | Static verification harness or fixture runner exceeds deadline | Item remains leased/retryable in Muster; Bellbuoy deduplicates repeated timeouts by fingerprint. |
| `E_NEEDS_SUBTOOL` | Unrecognized bundle or assertion format introduced by a new template | Fails closed, pauses item in `needs_subtool`, and triggers Bellbuoy to open a task; auto-replays once Shipkeeper deploys the fix. |

## Security & Clean-Room Boundaries

- **Network isolation:** Default-deny network policies block Shakedown from reaching Logbook, Plainforge, or Lazarette directly.
- **Unprivileged execution:** Runs as non-root with dropped Linux capabilities, no privilege escalation, and a read-only root filesystem (apart from `/var/spool/cs`).
- **Clean-room & data hygiene:** Verification fixtures must use synthetic or public data only; real CUI, proprietary contractor rates, and non-public solicitation text are strictly rejected. No raw Sextant observation artifacts ever cross into Shakedown.
- **Sanitized reporting:** Shipkeeper strips internal IPs, node names, and pod hostnames before any failure status reaches `pub.*` or `https://clearedstack.com/platform/#registry`.
